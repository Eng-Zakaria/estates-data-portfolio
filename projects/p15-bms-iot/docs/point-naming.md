# Point naming

## The rule

```
point_id = <building>.<equipment>.<point_class>
topic    = campus/<building>/<system>/<equipment>/<point_class>
```

```
B001.ahu_01.supply_temp
campus/B001/ahu/ahu_01/supply_temp
```

The registry is generated by `src/make_registry.py` into
`src/point_registry.csv` and committed, because the Node-RED flow looks points
up from it at runtime. The generator is the source of truth: regenerate rather
than editing the CSV, and `tests/test_registry.py::test_committed_registry_matches_the_generator`
fails if they disagree.

## Registry columns

| column | example | notes |
|---|---|---|
| `point_id` | `B001.ahu_01.supply_temp` | primary key in `bms.points` |
| `building` | `B001` | matches the topic segment |
| `system` | `ahu` | the service: `ahu`, `boiler`, `pump`, `room` |
| `equipment` | `ahu_01` | zero-padded so a lexical sort matches the numeric order |
| `equipment_kind` | `ahu` | the template the equipment came from; used to pick fault targets |
| `point_class` | `supply_temp` | what is measured |
| `unit` | `C` | canonical unit; asserted to match the contract |
| `topic` | `campus/B001/ahu/ahu_01/supply_temp` | 1:1 with `point_id` |
| `source_address` | `SYNTH/B001/AHU_01/AI.supply_temp` | **placeholder**, see below |

### `source_address` is a placeholder, not a device address

The values are shaped like a BACnet object reference so the column has the right
*shape* for a real integration, but `SYNTH/` is not an object instance and
nothing resolves it. In a live deployment this column is populated from the
site's BACnet object list or the Modbus register map, not from this generator.
See [`mapping-to-real-systems.md`](mapping-to-real-systems.md).

## Naming decisions worth defending

**Dots in `point_id`, slashes in topics.** The two are different namespaces: the
topic is a wire address, the `point_id` is a database key. Keeping them
structurally different means a point_id can be embedded in a CSV column header
(`B001.ahu_01.supply_temp [C]`) without quoting problems, and a topic can be
matched with a plain `campus/#` subscription.

**`equipment` before `point_class` in both.** Grouping by equipment is the
common access pattern (every question about an AHU wants all its points), and
it makes the valve-pairing rules in `src/health.py` a string operation: the
paired point of `B001.ahu_01.heating_valve` is found by replacing the point
class, because the equipment prefix is already shared.

**Zero padding.** `room_02` sorts before `room_10`; `room_2` would not.

**Building codes, not names.** `B001` rather than "Harkney Building": the code
is short, stable under a rename, and matches the `B\d{3}` pattern the contract
enforces. The estate register (in the P01 lakehouse) holds the mapping from code
to name, so the warehouse is the place that resolves a code to something a
report can print.

## Adding a point

1. Add the `point_class` to `POINT_UNITS` and `EQUIPMENT_TEMPLATE` in
   `src/make_registry.py`.
2. Add its unit and plausible range to `rules_by_point_class` in
   `contracts/validation_rules.json`. This is a deliberate second step: the
   contract is the thing the running pipeline reads, and a point class with no
   range would be rejected at runtime with no useful message.
3. `make iot-registry` and `make iot-dashboards`.
4. If the new point needs a value in the simulator, add a branch to
   `Simulator.value_for`. A point class with no branch raises rather than
   defaulting, because a silent zero looks like working plant.
5. `make iot-test`. The registry tests assert uniqueness, contract agreement and
   that the committed CSV matches the generator.

## Point classes in this demo

294 points across 3 buildings:

| equipment kind | per building | point classes | points |
|---|---|---|---|
| AHU | 3 | supply_temp, return_temp, damper_pos, fan_speed, heating_valve, cooling_valve, sub_meter_kwh | 21 |
| boiler | 2 | supply_temp, heating_valve, sub_meter_kwh | 6 |
| pump | 3 | sub_meter_kwh | 3 |
| room | 17 | room_temp, setpoint, co2, occupancy | 68 |

That is 98 plant points and 204 room points per building-set, matching the
spec's "~20 plant items and ~50 rooms across 3 buildings".

The AHU count is three rather than two because the valve fault rules need
disjoint equipment: a stuck heating valve and a planted heating-and-cooling
fault on the same AHU make the two faults indistinguishable, and
`tests/test_simulator.py::test_simultaneous_heat_cool_avoids_the_stuck_valve_equipment`
enforces that.
