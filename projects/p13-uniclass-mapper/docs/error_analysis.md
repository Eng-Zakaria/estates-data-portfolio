# P13 error analysis

All numbers below were produced by `make p13-eval` (`python projects/p13-uniclass-mapper/src/eval.py --seed 42`)
on 2026-10-08 and are reproduced verbatim in the README. The golden set is 1,324 rows
split once, stratified by label: **train 909 / dev 187 / test 228**. Thresholds are
tuned on **dev only**; the test split is read once for the numbers below.

> Reminder from `docs/SOURCES.md`: labels were drafted against a **non-authoritative
> placeholder** code list, so these measure agreement with synthetic labels, not
> real-world Uniclass accuracy.

## 1. Method comparison (top-1 / top-3 accuracy)

| Method | train (909) | dev (187) | **test (228)** |
|---|---|---|---|
| Fuzzy baseline (`rapidfuzz` token-set on titles) | 18.04% / 56.33% | 17.65% / 57.22% | **21.49% / 60.96%** |
| Embedding retrieval (`all-MiniLM-L6-v2`, cosine top-k) | 57.43% / 80.64% | 56.68% / 81.82% | **57.02% / 81.14%** |
| Hybrid (0.4 fuzzy + 0.4 embedding + 0.2 keyword, plus tag / synonym / table rules) | 98.46% / 99.78% | 98.40% / 98.93% | **97.81% / 99.56%** |

Reading it honestly:

- The fuzzy baseline is weak on purpose: a description like *"humidity sensor AHU"* shares
  almost no tokens with the title *"Sensors"*. Token overlap is the wrong tool for
  abbreviations and near-synonyms.
- Embeddings recover a lot (57%) but cannot separate sibling codes whose titles differ
  by one word (*fan coil* vs *fan coil units*), which is why top-3 (81%) is so much
  higher than top-1 (57%).
- The hybrid score is the sum of the two plus explicit keyword rules. It is not a
  learned model and it has no held-out hyperparameters beyond the three weights; they
  were set by inspection and **not** swept, so they cannot be accused of test tuning.
- The residual gap between train (98.46%) and test (97.81%) is small, so there is no
  sign of memorisation of the training split.

## 2. Confidence policy

`eval.tune_thresholds` sweeps τ_high over 0.30–0.95 on dev and keeps the threshold with
the **highest auto-accept rate** among those reaching ≥ 95% auto-accept precision
(ties → higher precision, then higher threshold).

| | value |
|---|---|
| τ_high (dev-tuned) | **0.30** |
| τ_low (dev-tuned, clamped to τ_high) | **0.30** |
| Dev auto-accept rate | 100.0% (187/187) |
| Dev auto-accept precision | **98.40%** (184/187) — target was ≥ 95% ✔ |
| Test auto-accept | 227/228 = 99.56%, precision **98.24%**, review 0, reject 1 |

Two things this table does *not* tell you, and should not be hidden:

1. **The review queue is empty by construction.** Because the dev-tuned τ_high (0.30)
   fell below the default review floor (0.45), `eval` clamps τ_low up to τ_high and the
   review band `[τ_low, τ_high)` is empty: on this data set nothing scores between the
   two. In production the shipped defaults (`hybrid.CONFIDENCE_THRESHOLDS`: auto ≥ 0.85,
   review ≥ 0.45, reject below) are the safer policy — measured on dev they auto-accept
   74/187 rows and send the remaining 113 (99 review + 14 reject) to a human. The CLI
   supports both: `pipeline.py --tau-high 0.30 --tau-low 0.30` reproduces the tuned
   policy, omitting the flags uses the shipped defaults.
2. **Precision 98.40% at τ_high = 0.30 is the wrong headline on its own.** It is high
   because this golden set is generated from templates around a 96-code vocabulary, so
   almost every description has a near-exact title match. On messier, real free text the
   low-score band would fill up and the tuned threshold would have to move up.

## 3. Calibration (test split, 5 bins)

| hybrid score bin | n | empirical top-1 accuracy |
|---|---|---|
| 0.00–0.20 | 0 | — |
| 0.20–0.40 | 7 | 85.7% |
| 0.40–0.60 | 49 | 91.8% |
| 0.60–0.80 | 64 | 100.0% |
| 0.80–1.00 | 108 | 100.0% |

Diagram: `docs/img/calibration.svg` (generated by `eval.calibration_svg`, no plotting
dependency). The curve sits *above* the diagonal in the 0.4–0.6 band, i.e. the score is
optimistic there: a 0.5 score is right only ~92% of the time. Every test error sits at
or below 0.536, so the whole error mass is in the two lowest bins. The trade-off, swept
on test only to *describe* the curve (no threshold was tuned on it):

| τ_high | auto-accepted | auto-accept rate | auto-accept precision |
|---|---|---|---|
| 0.30 (dev-tuned, reported) | 227/228 | 99.56% | 98.24% |
| 0.40 | 221/228 | 96.9% | 98.19% |
| 0.50 | 208/228 | 91.2% | 98.08% |
| **0.60** | 172/228 | 75.4% | **100.00%** |
| 0.85 (shipped default) | 102/228 | 44.7% | 100.00% |

So a τ_high of 0.60 gives a **perfect** auto-accept band and costs 24 percentage points
of throughput; the shipped default of 0.85 sends 55% of rows to a human. The spec asked
for the largest auto-accept rate subject to ≥ 95% precision, which is what is reported —
but 0.60 is the number I would actually deploy for a first handover pass.

## 4. Most-confused pairs (test split, all 5 errors)

| true code | predicted code | count | score | why |
|---|---|---|---|---|
| `Pr_50_10_20` (Radiators / heat emitters) | `Pr_50_10` (parent) | 4 | 0.536 | all four are *"underfloor heating …"* — the parent title "Heat emitters" and the leaf title differ only by the discriminator "underfloor", which the matching query does not treat as a leaf-specific token, so the parent wins on the shared-word count |
| `Pr_50_40` (Water supply) | `Pr_50_20_20` (Fan coil units) | 1 | 0.215 | *"dosing pot chemical"* — no token in common with the correct ancestor, so the low-score embedding term carried the row |

Both are **hierarchy** errors, not taxonomy errors: the model picks a real ancestor
(first case) or an unrelated cousin (second). Fixing the first properly needs the
parent/sub-tree score (a depth penalty when the description carries a leaf-specific
discriminator such as "underfloor"), which is listed as next work in README §8 rather
than tuned into this run. The second is simply a low-signal description and is exactly
what the review queue exists for.

## 5. Review-loop round trip (dev split, empty synonym store)

| | value |
|---|---|
| Dev top-1 with an **empty** `synonyms.csv` | 78.61% (147/187) |
| Human overrides recorded (exactly the 40 wrong rows) | 40 |
| Dev top-1 after feeding those overrides back | **98.93%** (185/187) |

This is the active-learning loop measured end-to-end (`tests/test_p13.py::
test_review_ui_round_trip`, the `Streamlit` review UI writes through the same
`synonyms.record_decision` path). The shipped `data/synonyms.csv` holds 52 curated
phrases and reproduces the 98.40% dev figure quoted above.

**Two rows stayed wrong even after an override**, which is worth stating because it
bounds what the loop can do:

| description | true code | still predicted | score | why the override did not win |
|---|---|---|---|---|
| `roof extract fan` | `Pr_50_20_10` | `Pr_50_20_40` | 0.498 | the synonym bonus (+0.25) is deliberately bounded so a human override cannot outvote overwhelming evidence; the competing candidate scored 0.75 from the embedding term alone |
| `humidity sensor AHU` | `Pr_50_60_20` | `Pr_50_20_10` | 0.776 | the description names two pieces of plant ("sensor" + "AHU"); the tag rule reads the leading token `humidity` as no signal and the embedding term prefers the air handling unit |

The first is a scoring-policy question (the bounded bonus is a design choice, not a
bug). The second is a genuine ambiguity in the *description*: a sensor inside an AHU is
a sensor, but the string contains the AHU tag. Real register data would need a
"dominant asset vs contained sensor" rule, which is out of scope for this project.

## 6. Where the embedding model hurts

`src/normaliser.py:matching_query` strips location tokens (`roof`, `plantroom`,
`rm 214`), manufacturer names and pure numbers before embedding. Without that strip,
*"LED panel light office"* retrieved **Roofs** and *"pressure sensor duct"* retrieved
ducts rather than sensors. Those two failures were found by inspecting the worst dev
rows, fixed in the matching query (not in the model, not in the test split), and are
covered by `test_normaliser` / `test_fuzzy_matching`.

## 7. Metric caveats

- Top-1/top-3 are computed on the *unweighted* label space; there is no per-class
  weighting, so a code with 40 template rows counts more than one with 3.
- The golden set is template-generated, so variants of the same phrase appear in train
  and test. The split is stratified but **not** deduplicated by phrase; with the official
  tables and real descriptions this would inflate the hybrid numbers further.
- `is_mock = true` throughout: see §1 above.
