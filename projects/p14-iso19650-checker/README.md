# P14: ISO 19650-style convention checker

> **Synthetic data for portfolio demonstration. No real project or compliance status is implied.**

## 1. Problem statement

A BIM or estates information manager needs every delivered file to carry an identifier that says what
it is, who produced it, which volume and level it belongs to, how current it is and whether it may be
relied on. In practice a project produces hundreds of files, and nothing enforces that: names drift into
lower case, revisions jump from P01 to P03, a published container sits in the WIP folder, the same
identifier is uploaded twice, a file lands in the CDE without ever being registered. Auditors then find
the gaps by hand, weeks later. This checker validates file and container names against **whatever
convention the organisation has written down** — the field order, widths, code lists, separator, CDE
state folders and status codes all come from a YAML file — and exits non-zero so a CI job can block a
delivery that would break the convention. It can also propose and apply the small subset of fixes that
are unambiguous (case and separator), with a rollback log.

## 2. Architecture

```mermaid
flowchart LR
    FOLDER[folder tree<br/>WIP / Shared / Published / Archive] --> CHECKER[checker.py<br/>structural: count/length/charset/pattern/codes<br/>semantic: status vs state, duplicates,<br/>number + revision gaps<br/>metadata: title / IFC project name]
    CONFIG[conventions/*.yml<br/>fields, widths, code lists,<br/>separator, state map, limits] --> CHECKER
    CHECKER --> ISSUES[issues<br/>rule_id, severity, field, message,<br/>suggested fix]
    ISSUES --> REPORT[text / HTML / JSON / JUnit]
    ISSUES --> REGISTER[container_register.csv<br/>+ sha256 per container]
    ISSUES --> SUMMARY[compliance_summary.csv<br/>by field / folder / originator]
    ISSUES --> SUGGEST[suggested_renames.csv]
    SUGGEST --> APPLY[apply (dry run default)<br/>rename_log.csv] --> ROLLBACK[rollback<br/>sha256 verified]
    REPORT --> GATE[exit code 1 → CI gate]
```

Modules: `checker.py` (config model + rules), `metadata.py` (optional document readers), `rename.py`
(apply/rollback with an audit log), `reporting.py` (text/HTML/JSON/JUnit), `cli.py` (Typer),
`make_sample.py` (deterministic sample project + truth file).

## 3. Data: sources, licences, synthetic note

- **The convention is the data.** `conventions/uk_national_annex.yml` encodes the information container
  identification convention published in the CDBB *BIM Toolkit | National Annex Guidance*
  (https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf, read 2026-10-06), with statuses in use
  taken from UK BIM Framework *Guidance Part C, Edition 1* (read 2026-10-06). Field widths, code lists
  and the revision format are quoted and located in [`docs/SOURCES.md`](docs/SOURCES.md).
- `conventions/estates_cde_variant.yml` is an **organisation-specific** second configuration (not a
  standard) used to prove the engine is convention-agnostic.
- Every file in the sample project is generated by `make_sample.py` with a fixed seed. `.docx` files are
  written with python-docx; `.ifc`, `.pdf`, `.xlsx` and `.dwg` entries are text placeholders and the
  checker reports them as `metadata:placeholder:<ext>` rather than pretending to read them.
- No real project files, no employer data, nothing downloaded into the repo.

## 4. Quick start

```bash
make p14-sample                                                  # generate the seeded sample (301 files)
make p14-check                                                   # check it, print the report, exit 1
python projects/p14-iso19650-checker/src/cli.py check data/iso19650/sample --format junit --out data/iso19650/report
```

Or without make:

```bash
python projects/p14-iso19650-checker/src/make_sample.py --out data/iso19650/sample --n 300 --seed 42
python projects/p14-iso19650-checker/src/cli.py check data/iso19650/sample --config projects/p14-iso19650-checker/conventions/uk_national_annex.yml --suggest
python projects/p14-iso19650-checker/src/cli.py check data/iso19650/sample --format junit --out data/iso19650/report
```

## 6. Design decisions and trade-offs

- **Everything from config.** Field names/order/widths/charsets/patterns/code lists, separator, case
  policy, illegal characters, extension allowlist, path limits, CDE state folders and their statuses,
  sequence and revision rules, metadata rules. The engine contains no ISO/UK code list at all; a
  convention file is validated on load (duplicate positions, unknown field references, contradictory
  lengths all fail loudly) and its provenance (`source:` block) is shown in the HTML report footer.
- **Duplicates are scoped to (state, id, revision).** ISO 19650 keeps a container identifier stable
  across revisions and moves the container between states, so the same id in `WIP` and `Archive` is the
  lifecycle, and the same id with `P01`/`P03` is a revision history. Flagging either would have been a
  false positive; both are handled by the revision-gap rule instead.
- **Gaps are warnings, not errors.** A missing `0003` may simply mean the container was never produced.
  Warnings never fail the default `--fail-on error` gate.
- **Suggestions are self-verifying.** `--suggest`/`--apply` only offer a rename after re-checking the
  corrected stem and finding *zero* structural errors, so an applied rename cannot introduce a new
  violation. Case and separator slips are the only fixable classes; anything else needs a human.
- **Metadata checks are optional and honest.** Backends are imported lazily; a missing dependency, an
  unreadable container or a file whose extension does not match its content is reported in
  `skipped_checks` — never silently passed. A name that does not parse cleanly is not also accused of a
  title mismatch, which would be a cascading false positive.
- **Path length is measured relative to the checked folder**, so a report does not change because it was
  run from a different directory. Absolute-path problems belong to the CDE's own limits.
- Full trade-off list: [`SPEC.md`](SPEC.md) (implementation mapping and deviations).

## 7. Data quality and testing approach

`make p14-test` → **83 tests, 94% statement coverage** (`checker.py` 97%, `make_sample.py` 93%,
`rename.py` 92%, `reporting.py` 95%, `cli.py` 91%, `metadata.py` 91%).

| Test file | Covers |
|---|---|
| `tests/test_checker.py` | Every rule against hand-written names: width bounds, charset, pattern, code list, case, empty field, illegal character vs separator misuse, extension, stem/path length, status vs state, status globs, duplicate scoping, revision parsing, folder-scoped number gaps, revision gaps per P/C series, orphans, metadata agreement, registers, summaries, compliance maths, self-verifying suggestions |
| `tests/test_conventions.py` | Both shipped conventions load, declare provenance and match the published Annex tables (field widths, 28 type codes, 19 discipline codes, revision pattern); eight malformed conventions are rejected at load; one name judged by two conventions; determinism |
| `tests/test_sample.py` | Acceptance: every planted rule is reported against its own file, all 20 categories fire, seeded series gaps are exactly the reported ones, **zero false positives** on clean samples for both conventions, generator determinism |
| `tests/test_rename.py` | Dry-run writes a plan and touches nothing; apply → rollback restores the tree byte-for-byte; case-only renames (Windows case-insensitivity); rollback refuses edited content, an occupied target, a missing source and dry-run rows |
| `tests/test_cli.py` | All four report formats, exit codes 0/1, `--fail-on`, `--suggest` without touching disk, `--register` orphans, apply/rollback round trip, second convention |
| `tests/test_metadata.py` | Each optional backend when installed (skipped otherwise), magic-byte screening, missing backend / unreadable container / no title reported as skipped, case-sensitivity toggle |

Three bugs found by these tests are worth recording, because each would have shipped silently:

1. `Issue()` field attribution was passed positionally into `suggested_fix`, so `status_container_mismatch`
   and `revision_format` findings lost their field and dropped out of the by-field summary.
2. `separator_misuse` could never fire (it compared the illegal character against the convention
   separator, which is never itself illegal); it now fires when using the character as a separator would
   produce the expected field count.
3. Rollback treated dry-run log rows as applied, and on a case-insensitive filesystem it refused to undo
   case-only renames because both names "exist". Both fixed and covered by tests.

## 8. Scope: what is configurable, and what is **not** checked

Honest scope, per the spec.

**Configurable (any convention file the organisation writes):** number and order of fields; each field's
name, exact/min/max width, character set, regex pattern, closed code list, required flag and case
policy; the separator; which fields form the container identifier; illegal characters; extension
allowlist; stem and path length limits; CDE state folder names and the statuses valid in each (globs
allowed); sequential-number field and gap scope; revision field, WIP version suffix and gap warnings;
metadata rules (which formats to read, which identifier fields a title must contain, case sensitivity).

**Not checked — deliberately:**

- **Content.** Whether a PDF is the drawing it claims to be, or an IFC model is up to date, is out of
  scope. The metadata check compares the *declared title* with the *declared name*, nothing deeper.
- **Real IFC validation.** The IFC path only reads the header's project name; schema validation,
  property sets, MVD compliance and geometry are P11/P12 territory.
- **Code lists are not authoritative.** `uk_national_annex.yml` carries the published level/type codes,
  but the Annex explicitly allows project-specific expansions, so those lists must be reviewed for a
  real project (see `docs/SOURCES.md` §1.3). A closed list would produce false positives.
- **The status-to-state map is an example**, derived from the Part C worked progression; the guidance
  requires the appointing party to record the real map in the project information standard.
- **No CDE integration.** The checker reads a folder; it does not talk to a CDE API, cannot see status
  metadata that is not in the file name, and does not know about approvals, transmittals or audit trails.
- **No git history awareness.** Renames are filesystem operations with a rollback log; the tool does not
  create commits, branches or pull requests.
- **Symlinks, case-only collisions inside a single directory on Linux, and non-ASCII normalisation**
  are not modelled beyond the illegal-character list.

## 9. What I would do next with real data

1. Take the organisation's real information standard and encode it, then run the checker in
   `--fail-on none` mode for a month to measure the false-positive rate against real filenames before
   gating anything.
2. Read status/revision from a CDE export (CSV/JSON manifest) instead of inferring them from the file
   name, and add the "container exists in the CDE but not on disk" direction to the orphan check.
3. Generate a correction plan per container id across a whole revision series (rename the current
   revision *and* its archive history consistently), with a dry-run diff reviewed by the information
   manager.
4. Emit the register in the shape ISO 19650-2 expects for a container register (including approval and
   revision history) so it can be loaded back into the CDE.
5. Wire the pre-commit hook and GitHub Action in `examples/` into a real repository once a committed
   sample project exists to test against.
