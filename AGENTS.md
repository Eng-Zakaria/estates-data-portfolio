# AGENTS.md: Estates Data Portfolio

Put this file at the **root of the repo**. Put the other spec files in `docs/specs/`. opencode reads `AGENTS.md` automatically; tell it to read the spec for the project it is working on.

## Mission

Build a portfolio of 20 data projects that demonstrate the skills in a University Estates "Data Analyst" role (data pipelines, integration of space/asset/meter/BIM data, Power BI reporting, data quality, standards, sustainability reporting). The audience is a hiring panel reading GitHub repos and screenshots. Quality, honesty and reproducibility matter more than size.

## Hard rules (never break)

1. **Synthetic or public data only.** Never use data from an employer, a university or any private source. Every dataset is either generated by `campus_synth` or downloaded from a public source whose licence permits reuse.
2. **Label synthetic data as synthetic** in READMEs, dashboards and chart footers. Never imply real results, real buildings' performance, or real compliance status.
3. **Provenance.** Every external dataset, standard, code list or conversion factor gets an entry in `DATA.md`: name, URL, licence, version/year, retrieval date, what it is used for. Do not commit data whose licence forbids redistribution; commit a download script instead.
4. **Never invent standard codes, factors or rules from memory.** This covers Uniclass codes, COBie field rules, ISO 19650 code lists, DESNZ emission factors, HESA/TRAC categories and statutory inspection frequencies. Fetch them from the official source and record the URL. If you cannot fetch them, stop and write the gap into `docs/OPEN_QUESTIONS.md` for the human, and use a clearly named `*_dev_placeholder*` file in the meantime. Where a spec describes a convention "from memory", treat it as a hypothesis to verify.
5. **Verify fast-moving APIs before coding**: Great Expectations, Airflow (2.x vs 3.x import paths), dbt (unit tests, contracts), IfcOpenShell, sentence-transformers. Read the pinned version's docs; do not rely on memory.
6. **No secrets in the repo.** Use `.env.example`. No default passwords in non-demo configs; demo passwords are labelled `DEMO ONLY`.
7. **Reproducible.** Seeded randomness, pinned dependencies (`uv.lock`), `docker compose` for services. A clean clone must run with the commands in the README.
8. **Tests first for validators and calculations.** Anything that computes a KPI, validates a rule or maps a code has unit tests with hand-checked fixtures.
9. **Honest metrics.** Report measured numbers (accuracy, recall, runtime) exactly as measured, including weak ones, and explain them. Do not tune on the test set.
10. **Do not commit** large generated data, `.pbix` binaries over ~25 MB, or model weights. Use `.gitignore` plus `make data`.

## Stack defaults (override only with an ADR in `docs/adr/`)

Python 3.12, `uv` for env/deps, `ruff` (lint + format), `mypy` (strict on shared packages), `pytest` + `pytest-cov`, `typer` for CLIs, `pydantic` v2 for configs/contracts, DuckDB + Parquet as the analytical store, dbt-duckdb for transformations, Docker Compose for services, Mermaid for diagrams, MkDocs Material for docs, GitHub Actions for CI, Terraform for any cloud infra. Power BI is the BI tool (see handoff protocol below).

## Makefile contract

Root Makefile must provide: `make setup`, `make data` (generate synthetic data, small profile by default, `PROFILE=default` for full), `make test`, `make lint`, `make ci` (lint + type + test + dbt build + DQ), `make docs`, `make clean`. Each project adds `make pNN-run` (or similar) documented in its README.

## README template (every project)

1. One-paragraph problem statement in plain English (who needs this, what decision it supports).
2. Architecture diagram (Mermaid).
3. Data: sources, licences, synthetic-data note.
4. Quick start (max 3 commands).
5. Results: key numbers and screenshots (placeholders `docs/img/*.png` that the human fills for Power BI).
6. Design decisions and trade-offs (link ADRs).
7. Data quality and testing approach.
8. Limitations and what I would do next with real data.
9. Skills demonstrated (maps to job criteria IDs, for example `E2, E4, D3`).

Write for a non-technical reader first, then technical detail below.

## Definition of done (per project)

- [ ] Runs from a clean clone using README commands (verified in CI or in a fresh container)
- [ ] Tests pass; coverage for core modules ≥ 80%
- [ ] `ruff` + `mypy` clean
- [ ] README complete per the template; Mermaid diagram renders
- [ ] `DATA.md` updated; no licence problems
- [ ] Acceptance criteria in the spec each verified, with evidence in `docs/` (command output or a screenshot placeholder)
- [ ] `STATUS.md` row ticked with date and notes
- [ ] No TODO placeholders left unless listed in `docs/OPEN_QUESTIONS.md`

## Power BI handoff protocol (P06-P10 and any project with a dashboard)

Power BI Desktop is a Windows GUI tool and `.pbix` files cannot be reliably generated by an agent. For every dashboard project the agent must prepare everything so the human can build the report in about 1-3 hours, and must **not** block on producing a `.pbix`:

```
projects/pNN-*/powerbi/
  model.md          # tables, columns used, relationships (cardinality, direction), date table, hidden fields, RLS roles
  queries/*.pq      # Power Query M scripts loading CSV/Parquet from ../../data/gold (parameterised folder path)
  measures.dax      # every measure, with a comment explaining the business meaning and format string
  wireframe.md      # per page: purpose, ASCII layout, each visual (type, fields, filters, sort), slicers, tooltips, drill-throughs, bookmarks
  theme.json        # Power BI theme (accessible colours, fonts, consistent KPI card styling)
  build-guide.md    # click-by-click steps in the order to build it, plus a validation checklist (numbers to tie back to SQL)
  screenshots/      # empty; human adds PNGs
  README.md         # business questions as "question → insight → decision" lines
```

Also produce, as a stretch for each dashboard, a lightweight `streamlit_app.py` that mirrors the key pages from the same gold tables (so a live demo link is possible even if Power BI publishing is unavailable). A separate `validation/` SQL script must reproduce every headline KPI so the human can check the Power BI numbers.
Stretch only, do not block: PBIP/TMDL (text-based Power BI project) generation.

## Workflow for each project

1. Read `AGENTS.md`, `00-foundation-campus-synth.md` and the project's spec section completely.
2. Write `docs/PLAN.md` (tasks, risks, open questions). Ask the human only about true blockers; otherwise record assumptions in the plan.
3. Implement in small commits using conventional commit messages (`feat:`, `fix:`, `test:`, `docs:`).
4. Run `make ci`. Fix everything before moving on.
5. Complete README and docs; update `STATUS.md` and `DATA.md`.
6. Summarise what was done, measured results, deviations from the spec and open questions.

Work on **one project at a time**. Do not start the next until the definition of done is met.
