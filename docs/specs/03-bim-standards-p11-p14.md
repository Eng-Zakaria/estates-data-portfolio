# BIM and standards projects P11-P14

These show you can treat BIM as *data*, which is exactly how the job advert frames it ("BIM forms part of the data landscape... fundamentally about data quality, analytics, and insight generation rather than model authoring").

Standing rule for this group: **do not invent standard codes or field rules.** Fetch from official sources, record provenance in `DATA.md`, and flag gaps in `docs/OPEN_QUESTIONS.md`. Where a spec below describes a convention from memory, treat it as a hypothesis to verify.

Depends on: foundation; P01/P04 for loading into the lakehouse (optional until P11 is complete).

## P11: IFC → analytics pipeline

**Location:** `projects/p11-ifc-analytics/`
**Criteria:** E2, E4, E6, D5, D6
**Stack:** IfcOpenShell (Python; verify current API for the pinned version), pandas, DuckDB, Parquet, Typer, pytest.
**Goal:** extract spaces, elements, types, systems, properties and quantities from IFC into analytical tables, check model data quality, and reconcile the model against the space register.

### Inputs
1. A public sample IFC (buildingSMART Sample-Test-Files or IfcOpenShell test files; record licence in `DATA.md`; download via script, do not commit if the licence is unclear).
2. A **synthetic IFC** generated by `make_sample_ifc.py` using the IfcOpenShell API: project → site → building (aligned to campus building B003) → storeys → `IfcSpace` with `Qto_SpaceBaseQuantities` → distribution elements (AHUs, boilers, pumps, fan coils) with classification references, manufacturer/type property sets and system membership. Include deliberate defects: elements without type, without classification, without space containment, duplicate names, zero-area spaces, 12 rooms whose area differs > 10% from the register, 5 rooms missing from the model (match `ground_truth.yaml`).

### Outputs (Parquet, plus DuckDB views)
`ifc_project, ifc_storeys, ifc_spaces, ifc_elements, ifc_types, ifc_systems, ifc_system_members, ifc_properties_long (global_id, pset, property, value, unit), ifc_quantities_long, ifc_classifications`.

### Features
- Handle IFC2X3 and IFC4 (document differences encountered).
- Area from `Qto` where present, documented fallback otherwise (flag the source of each area value).
- Stable key = IFC GlobalId; crosswalk to `space_id`/`asset_id` via `entity_crosswalk` (see P18).
- **Model QA report** (HTML + CSV): counts by class; elements missing classification / type / space / required property sets; duplicate GlobalIds; zero or negative areas; spaces without storey; naming-convention conformance; completeness % per property set.
- **Reconciliation:** `recon_model_vs_register` (area delta per room, rooms in model not in register and vice versa, summary by building). Feeds the P03 cross-source checks.
- CLI: `ifc2tables model.ifc --out data/gold/ifc/`; incremental by file hash; log runtime vs element count.
- Power BI handoff: "Model data health" page and "Space & asset explorer" page (spec only).

### Acceptance
- All seeded model defects appear in the QA report (counts match the generator's log).
- All planted area mismatches and missing rooms found by reconciliation (100% recall).
- No geometry processing required (state this; extraction stays fast), runtime table documented.
- Works on both the public sample and the synthetic model; tests use a tiny fixture IFC committed to the repo.

**CV bullet:** *Built a pipeline that converts IFC models into queryable analytical tables with automated data-health reporting and model-vs-register reconciliation (100% of seeded discrepancies found).*

## P12: COBie validator and handover loader

**Location:** `projects/p12-cobie-validator/`
**Criteria:** E2, E6, E7, D3, D6
**Stack:** pandas, openpyxl, pandera or Pydantic, Jinja2, DuckDB, Typer, pytest.
**Goal:** validate a COBie workbook against rules and Asset Information Requirements, then load clean records into the operational asset register with an audit trail.

### Source research (required first step)
Find the public COBie specification (buildingSMART COBie pages and UK BIM Framework guidance): sheet list, column names/order, mandatory columns, keys and relationships. Record URLs/versions in `docs/SOURCES.md`. The sheet set is expected to include Contact, Facility, Floor, Space, Zone, Type, Component, System, Assembly, Connection, Spare, Resource, Job, Impact, Document, Attribute, Coordinate, Issue, Picture, but **verify** and implement what the spec says.

### Inputs
`make_sample_cobie.py` builds a valid workbook for a campus building plus a corrupted variant with ≥ 40 seeded errors across categories (missing sheets/columns, empty mandatory cells, duplicate keys, broken foreign keys, bad email or date formats, invalid category patterns, missing manufacturer/model/warranty/expected-life attributes, duplicate serial numbers).

### Rules engine (`rules/cobie.yml` + `rules/air.yml`)
- Structural rules from the spec: sheets present, columns present and ordered, mandatory fields.
- Keys and referential integrity: for example Component → Type, Component → Space (including multi-value cells), Space → Floor, System → Component, Job → Type, `CreatedBy` exists in Contact.
- Format rules: email, ISO 8601 dates, numeric ranges, category code pattern (regex; membership check against Uniclass if P13 reference data is available).
- **AIR rules** (editable YAML simulating an employer's Asset Information Requirements): required attributes per asset class (for example manufacturer, model, serial, warranty duration, expected life, installation date).

### Outputs
- Validation report (HTML with per-sheet summary and issue table, CSV, JSON). Each issue has sheet, row, column, rule id, severity (blocking / warning), message, suggested fix.
- **Handover readiness score** (weighted completeness) and an exit code ≠ 0 on blocking errors (usable in CI).
- **Handover loader:** maps COBie Type/Component/Space to staging tables → matches to existing assets (serial, IFC GlobalId, or space+type) → `inserted / updated / unchanged / rejected` counts; rejects to quarantine with reasons; load audit table; idempotent re-run; `--dry-run` produces a diff report. Maps COBie category to internal `asset_type`.

### Acceptance
- Every seeded error found with the correct rule id (confusion matrix by error category in README).
- Valid workbook: zero blocking errors.
- Loader is idempotent (second run = all unchanged); rejected rows carry reasons.
- Unit tests for each rule type; AIR change (edit YAML) changes results without code changes.

**CV bullet:** *Implemented a rules-driven COBie validator and handover loader with AIR-based completeness scoring, quarantine and audit logging, turning project handover into a repeatable, testable data process.*

## P13: Uniclass classification mapper

**Location:** `projects/p13-uniclass-mapper/`
**Criteria:** E6, D6 (also supports P12)
**Stack:** Python, rapidfuzz, sentence-transformers (small embedding model; verify availability and licence), scikit-learn, numpy/FAISS, Streamlit, DuckDB, pytest.
**Goal:** assign classification codes to messy free-text asset descriptions with confidence scores and a human review loop.

### Reference data (hard rule)
Download the **official Uniclass 2015** tables from NBS (at least Products `Pr` and Systems `Ss`; check the terms of use; record version/date in `DATA.md`). **Never invent codes.** If the download is not possible, stop and note it in `docs/OPEN_QUESTIONS.md`; for development use `mock_uniclass_dev_placeholder.csv`, loudly labelled non-authoritative, and make the pipeline refuse to produce "final" outputs from it.

### Golden set
Build ≥ 300 labelled examples: messy descriptions ("AHU-03 air hndlg unit L2", "Boiler no 2 (Remeha)", "FCU fan coil rm 214", "emerg lighting luminaire"...) × true codes. Foundation provides the asset types; the agent drafts labels against the *official* table; **the human must review a ≥ 20% random sample** (generate `review_sample.csv` for this) before reporting accuracy. Split train/dev/test once; never tune on test.

### Methods (compare all)
1. Text normalisation: lowercase, abbreviation expansion dictionary (AHU, FCU, VAV, PRV, MCC, UPS, etc.), tokenisation, stop-words.
2. Baseline fuzzy matching (`rapidfuzz` token-set ratio) against code titles + synonyms.
3. Embedding retrieval (top-k cosine).
4. Hybrid score (weighted fuzzy + embedding + keyword-rule sub-tree filter).
5. Optional LLM re-ranker behind an interface, **off by default**, no keys in the repo.

### Outputs
- `classification_results` (asset_id, top-3 candidates, scores, chosen code, confidence band, matched-term explanation).
- Confidence policy: auto-accept ≥ τ_high; review queue between τ_low and τ_high; reject below. Choose thresholds on the dev set to hit ≥ 95% precision for auto-accepts; report the resulting auto-accept rate.
- **Streamlit review UI:** accept / override / note; decisions saved to `human_decisions` and fed back into `synonyms.csv` (active-learning loop).
- Metrics: top-1 and top-3 accuracy per method, precision/recall of auto-accept, confusion on the most-confused pairs, calibration plot, error analysis (`docs/error_analysis.md`).

### Acceptance
- All reported numbers reproduced by `make eval` from fixed seeds; numbers pasted into the README exactly as measured.
- Normaliser unit-tested; no secrets; pipeline can run offline after model download.
- Review UI round-trip test (decision → synonyms update → improved or unchanged accuracy on dev).

## P14: ISO 19650-style compliance checker

**Location:** `projects/p14-iso19650-checker/`
**Criteria:** E6, E7, D6
**Stack:** Python, Typer, Pydantic, PyYAML, Jinja2, pytest; optional ifcopenshell/openpyxl/python-docx/pypdf for metadata.
**Goal:** a convention-agnostic checker that validates file/container naming and metadata against a configurable information-management convention.

> **Verify the convention first.** The spec's author recalls a typical UK-style field pattern *(Project – Originator – Volume/System – Level/Location – Type – Role – Number, with status/suitability and revision)* but has not verified code lists or lengths. Read the UK BIM Framework / BS EN ISO 19650 UK National Annex guidance, record sources in `docs/SOURCES.md`, and encode what you find in `conventions/uk_example.yml`. The engine must read **everything** from config so an organisation's own convention can be dropped in; ship a second, different convention in tests to prove it.

### Checks
Field count, order, length, charset and separators; values against allowed code lists; sequence number format; revision format and sequencing gaps; status/suitability code vs container state (WIP / Shared / Published / Archive folder); duplicate identifiers; case and illegal characters; path length; disallowed file types; metadata consistency (filename vs document title or IFC project name where available); orphan files missing from the container register.

### Features
- `iso19650-check <folder> --config conventions/uk_example.yml --format html|json|junit`
- `--suggest` mode lists fixes for trivially fixable issues (case, separators) and never renames; `--apply` renames with a dry-run default and a rollback log.
- Generates `container_register.csv` and a compliance summary (compliance % by field, by folder, by originator).
- Sample project folder generator (~300 files, seeded issues of every category, logged to a truth file).
- Pre-commit hook and GitHub Action examples; JUnit output for CI.

### Acceptance
- Every seeded issue category detected; false positives = 0 on the clean sample.
- Swapping convention file changes behaviour with no code edits (test with two conventions).
- `--apply` is reversible (rollback test).
- README lists what is configurable and what is *not* checked (honest scope).
